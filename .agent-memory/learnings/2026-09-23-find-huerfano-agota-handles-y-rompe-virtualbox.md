# Learning — `find /` huérfano de un agente agota la tabla de handles y rompe VirtualBox

[Error] VirtualBox fallaba al arrancar cualquier VM con `NtCreateFile(\Device\VBoxDrvStub) failed: -35` / `NtQuerySystemInformation/SystemExtendedHandleInformation failed: 0xc0000004` (supR3HardenedWinReSpawn). El mensaje apunta al módulo del kernel ("Make sure the kernel module has been loaded successfully"), pero los drivers VBoxSup/VBoxNetLwf/VBoxUSBMon estaban cargados y corriendo: pista falsa.

[Causa raíz] Tres procesos `C:\Program Files\Git\usr\bin\find.exe / -iname <algo>.jar` lanzados por agentes (búsqueda de jars barriendo TODO el disco) quedaron huérfanos desde el día anterior y acumulaban **31,7 millones de handles** entre los tres. El arranque endurecido de VirtualBox consulta la tabla global de handles del sistema; con esa tabla gigante la consulta falla con `STATUS_INFO_LENGTH_MISMATCH` y el proceso VM no llega a arrancar. Tras matarlos, el total del sistema bajó a ~200.000 handles y la VM arrancó a la primera.

[Solución] Ante cualquier fallo raro de arranque de VirtualBox/Hyper-V/WSL en esta máquina, medir primero `Get-Process | Measure-Object Handles -Sum` y revisar el top por handles antes de sospechar de drivers o de Core Isolation. Y sobre todo, **prohibido `find /` (o `find` desde la raíz de un disco) en los agentes**: barre el disco entero, tarda horas, queda huérfano cuando el agente termina y filtra handles sin límite. Para localizar un jar: usar el índice de contratos, `mvn dependency:build-classpath`, o acotar la búsqueda a `~/.m2` con Glob/Grep.
